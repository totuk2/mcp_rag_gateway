# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Homelab MCP Gateway + Tool-RAG: a single Starlette/uvicorn service that proxies multiple upstream MCP servers (stdio, SSE, Streamable HTTP) behind one authenticated `/mcp` endpoint, plus a semantic tool-retrieval API (`/tool-rag/*`) so AI clients (e.g. LibreChat Deferred Tools) discover tools at runtime instead of loading the full catalog into context. The full design spec lives in `content.md` (in Polish).

## Commands

```bash
# Run the gateway (from this directory; venv in .venv)
python -m gateway                      # uvicorn on 0.0.0.0:8765

# Provision upstream servers from servers/*/manifest.yaml (see below)
python provision.py                    # or: make provision  (--host for host-run gateway)

# Docker
docker compose up --build              # gateway only; mounts ./config read-only; DB+index+catalog in the tool-rag-data volume
make up                                # provision + gateway + provisioned docker servers

# Install deps
pip install -r requirements.txt
```

## Adding upstream servers (provisioning)

`provision.py` turns a per-server `servers/<id>/manifest.yaml` into runnable config.
To add a server: drop sources (or `git clone` a repo) into `servers/<id>/`, add a
`manifest.yaml` (see `servers/MANIFEST.example.yaml`), run `python provision.py`, restart
the gateway. Tool-RAG resyncs and reindexes on startup, so the tools register themselves.

Manifest `kind`:
- `stdio` — runs `setup` once (fingerprinted via a `.provisioned` marker; `--force` re-runs), registers a stdio subprocess entry.
- `docker` — emits a service (with a `build:` context) into `docker-compose.servers.yml`, registers a `streamable_http`/`sse` URL (service name in compose, or `127.0.0.1:<port>` with `--host`). The image is built by `docker compose up --build`, not by the provisioner — so provisioning can itself run in a container with no Docker socket (`make up-docker` / `docker compose run --rm provision`). Manifest `env:` → service `environment:` (values pass through verbatim, so `${VAR}` is interpolated from the root `.env` by compose — keep server secrets there, not in the committed manifest); `env_file:` → service `env_file:` (paths relative to `servers/<id>/`, must stay inside the repo). `volumes: [name:/path]` → named volume `<id>-<name>` (declared top-level), for state that must survive `up --build`. `stdio` `env:` is passed to the subprocess literally (no interpolation, no compose).
- `remote` — registers an existing URL as-is.

When asked to "add a server from `<url>`/`<git repo>`", follow the **Agent playbook**
in README.md (the canonical step-by-step). In short: pick an `id`; classify the
source (running MCP URL → `remote`; repo with a `Dockerfile` → `docker`; repo that
runs as a process → `stdio`); for non-`remote`, `git clone <repo> servers/<id>` and
**read the repo's README** for the exact run command + transport; write
`servers/<id>/manifest.yaml`; `python provision.py`; grant the key in `keys.yaml`;
restart. Removing: delete `servers/<id>/`, drop its `keys.yaml` block, re-provision,
restart — the startup sync reconciles and prunes the server's tools.

Outputs are **generated, gitignored, never hand-edited**: `config/registry.generated.yaml`
and `docker-compose.servers.yml`. At startup `load_registries()` (registry.py) merges the
generated registry under the hand-written `config/registry.yaml`, and **hand-written entries
win on id conflict**. `servers/echo/` is the reference stdio example.

There is no test suite, linter config, or CI in this repo. The repo is not a git repository.

Smoke checks: `GET /health` (no auth), `POST /tool-rag/retrieve` with `{"query": "..."}`, MCP via `/mcp` with `Authorization: Bearer <key>`.

Configuration is entirely via env vars (see README.md table) + two YAML files in `config/`: `registry.yaml` (upstream servers) and `keys.yaml` (API keys → access policies). `servers/echo/` (manifest.yaml + server.py) is the reference stdio upstream.

## Architecture

Two packages compose into one ASGI app, assembled in `gateway/app.py:app_from_env()`:

**gateway/** — MCP proxy layer
- `app.py` — Starlette app factory; `APIKeyMiddleware` resolves Bearer token → `AccessPolicy` and stores it in a contextvar (`context.py`); lifespan hook runs the initial Tool-RAG sync + index build.
- `server.py` — the merged MCP `Server`. Every handler re-reads the request policy via `get_policy()`. **Admin lockdown:** non-admin keys see only the meta-tools (`find_tools`, `run_tool`, `run_tools`, `describe_tool`, `browse_tools`, `get_skill` when skills are visible, `delegate` when `TOOL_RAG_AGENT=on`, and `plan` when a planner is configured) plus tools discovered this session; admin keys also get the full catalog. **Meta-tools:** `run_tools` runs several discovered tools concurrently through `_dispatch_tool` (bounded by `TOOL_RAG_MAX_PARALLEL`, per-call error isolation); `find_tools` takes `include_schema` (false → name+desc shortlist, lazy mode) and `describe_tool` fetches one tool's full schema **and full description** on demand (via `retriever.get_tool()`) + registers it for strict clients; the `find_tools` shortlist advertises only a truncated *teaser* description (`TOOL_RAG_SHORTLIST_DESC_CHARS`, default 300; 0 = full) — full text stays in `describe_tool` and the embedding (presentational, no reindex); `plan` (gated on `planner`) gathers policy-scoped candidates and returns an LLM-built multi-step plan (advisory, never executed). `find_tools` is the in-band discovery entry point: calling it runs the Tool-RAG retriever **scoped to the key's allowed servers + `tool_prefixes`** (via `get_policy()`) and returns matching tools with `call_name` + `input_schema`. The raw `POST /tool-rag/retrieve` HTTP handler (`tool_rag/router.py`) is policy-scoped the same way (reads `current_policy`, narrows the body's `allowed_servers` to the key's grants, applies `tool_prefixes`); enforcement is skipped only under `TOOL_RAG_WITHOUT_AUTH=1` (no policy in context by design). The `Server` also sets the MCP `initialize` `instructions` field (only when Tool-RAG is on) telling agents to call `find_tools` first. `call_tool` still works for any allowed tool by name — including tools never listed (discovered via `find_tools`); strict clients that validate calls against the advertised list are a known limitation. The retriever is wired in via `build_gateway_server(registry, retriever=...)`.
- `backends.py` — `open_upstream_session()`: opens a *fresh* upstream session per request (stateless; no connection pooling — a stdio upstream spawns a new subprocess on every call). `_dispatch_tool` retries a failed call once when the upstream certainly didn't run it (429/502/503/504, connect errors; not for sticky sessions) and reports the root cause, not the anyio `TaskGroup` wrapper. Exception: servers flagged `stateful: true` (registry/manifest; e.g. `playwright`, whose open page is tied to the MCP session) go through `session_pool.py`.
- `results.py` — `ResultStore` + `project`/`view`: `run_tool`/`run_tools` `fields` (JSON paths `a.b`, `x[].y`, `x[0].y`) project results; `_shape_result` (in `server._dispatch_tool`) keeps the full text under a `result_id` whenever it shortens a result (projection, compact digest, > `RESULT_MAX_CHARS`); meta-tool `get_result` reads it (fields / grep / offset+limit). Per key, in memory, `RESULT_TTL_S`.
- `reloader.py` — `ConfigReloader`: every `CONFIG_RELOAD_INTERVAL` (10 s) applies changed keys.yaml (`KeyStore.replace`), registry*.yaml (in-place swap of the shared `Registry.servers` dict → app callback: full_sync + refresh_catalog + full_reindex + health probe + `session_pool.close_server`) and SKILL.md (`SkillStore.load`); invalid files keep the old config; `POST /tool-rag/reload` forces. Anonymous policy is resolved per request (`APIKeyMiddleware._anon_policy`). Avoid restarts — they drop clients' MCP sessions.
- `metrics.py` — `Metrics`: per (kind, tool) calls/errors/latency (p50/p95 from last 200)/background jobs, upstream raw vs sent chars, per-key call counts; `GET /tool-rag/metrics/tools`, `/tool-rag/metrics/prometheus`. Recorded in `handle_call_tool` (kind `call`) and `_dispatch_tool` (kind `upstream`).
- Tool reviews (quarantine): `ServerConfig.review_changes` (default `_is_external(url)`); `SyncAdapter._review` after a server's first sync: new tool → `status="quarantined"` (retriever/catalog only show `active`; `_dispatch_tool` blocks it), changed `ToolRecord.review_fingerprint` (name+description+input_schema) → approved fields kept; pending rows in `tool_reviews`; admin `GET /tool-rag/reviews`, `POST /tool-rag/reviews/{approve|reject}` (router.py).
- `jobs.py` — `JobStore`: `handle_call_tool` runs every call (except `get_job_result`) via `jobs.run()`; if not done within `TOOL_CALL_SYNC_SECS` (25) it returns `{"status":"running","job_id"}` and the task continues (contextvars incl. policy/request context are copied into it); `get_job_result` waits ≤20 s and returns the original `CallToolResult`. Per-key ownership, in-memory, 30 min TTL after completion.
- `compactors.py` — `compact(tool, args, text)`: for servers flagged `compact_results: true` (registry/manifest), `_dispatch_tool` replaces a flight-search result with a digest (≤ `COMPACT_MAX_OPTIONS` one-line options + total + how to get raw) for Kiwi `search-flight`, fli `search_flights`, Duffel `search_flights`/`search_multi_city`, Skiplagged `sk_flights_search`; parse failure → original. `run_tool`/`run_tools` items take `full: true` to bypass. `_result_to_json` (run_tools) omits `structuredContent` when text exists.
- `session_pool.py` — `StickySessionPool`: one held-open upstream session per (downstream MCP session, stateful server), each owned by its own background task (transport contexts must open/close in one task); calls are serialized per session; closed on idle (`STICKY_SESSION_IDLE_SECS`, 600), downstream-session GC (`weakref.finalize`), LRU over `STICKY_MAX_SESSIONS` (20), transport failure (one retry on a fresh session; `McpError` not retried) and shutdown. Used by `_dispatch_tool` only (run_tool/run_tools/direct/delegate). Playwright still needs `--shared-browser-context` (without it the page is lost even within a session), so concurrent downstream sessions share one browser.
- `merge.py` — namespacing: merged tool/prompt names are `{server_id}__{original}` (double underscore — `server_id` must never contain `__`); resources get opaque `gateway://{server_id}/{base64(uri)}` URIs.
- `registry.py` / `auth.py` / `policy.py` — YAML loaders; `AccessPolicy` gates per-server access with optional `tool_prefixes` / `uri_prefixes` / `prompt_prefixes` allowlists (empty = full access to that server).
- `tool_db.py` / `tool_record.py` — SQLite tool registry (source of truth for Tool-RAG); `ToolRecord` carries metadata like `tool_type` (read/write/admin/action/query), `permission_scope`, `status`.
- `sync_adapter.py` — connects to every upstream at startup, calls `list_tools()`, upserts into ToolDb; `_infer_tool_type()` heuristically classifies tools from name/description keywords. `full_sync()` also **reconciles**: tools whose `server_id` is no longer in the registry are deleted (removed servers don't orphan in the DB). Down-but-registered servers are kept (hidden at query time by liveness, not deleted).
- `skills.py` — `SkillStore`: loads `skills/<name>/SKILL.md` (frontmatter `name`, `description`, `requires_servers`); a skill is visible to a key only if it's granted all `requires_servers`; `match(query, policy)` = embedder cosine of query vs skill descriptions (≥ `SKILLS_MATCH_THRESHOLD`, 0.5). Used by `get_skill`, `find_tools` (`related_skill` hint), `browse_tools` (overview list + coverage `related_skill`) and `delegate` (auto-pick).
- `recipes.py` — `RecipeStore`: shared **site recipes** (browser-automation memory) in ToolDb table `site_recipes` (UNIQUE site+task; site = host without `www.`). `save` (writers: admin or keys granted `RECIPES_WRITER_SERVERS`, default `playwright`; size caps; `url_template` must stay on the recipe's domain; upsert counts a success, keeps label), `report` (success/failure counts), `find` (domain → parent domain → text over site/label/task; ranked successes−2·failures). `server._dispatch_tool` → `_with_recipes`: after a successful upstream call whose args contain an http(s) URL, appends `RecipeStore.as_context()` (fenced, labelled UNTRUSTED) once per MCP session per site. Meta-tools `get_site_recipes` / `save_site_recipe` (save listed only for writers); also given to the `delegate` sub-agent.
- `health.py` — `ServerHealth` tracks which upstreams are currently reachable; a background loop (`health_loop`) probes them every `TOOL_RAG_HEALTHCHECK_INTERVAL`s (concurrent via `asyncio.gather`, stdio treated as always-up). The retriever drops tools of down servers. Fail-open: empty down-set ⇒ all up.
- `index_publisher.py` — bridges ToolDb changes into the FAISS index (used by the `incremental` startup mode).

**tool_rag/** — semantic retrieval layer
- `embedder.py` — `create_embedder()` factory: `LocalEmbedder` (sentence-transformers all-MiniLM-L6-v2, 384-dim, lazy-loaded) or `ApiEmbedder` (OpenAI/Ollama-shaped HTTP), selected by `TOOL_RAG_EMBEDDER=local|url` (`api` = legacy alias for `url`). `ApiEmbedder` **L2-normalizes** returned vectors (remote APIs like Ollama return unnormalized vectors; the index is `IndexFlatIP`, so normalization recovers cosine == semantic_score ∈ [0,1]); its dimension comes from `TOOL_RAG_EMBED_DIM` else a one-shot probe. Changing the embedder forces a clean index rebuild regardless of reindex mode — `indexer._load()` rejects a persisted index whose `dim` **or** `embedder` (the `model_id`: `local:<name>` / `url:<url>#<model>`) ≠ the current embedder's. This catches same-dimension model swaps that the dim check alone would miss (stale vectors under `incremental`/`off`).
- `planner.py` — optional `create_planner()` factory (`TOOL_RAG_PLANNER=off|llm`, default off): `LlmPlanner` calls an OpenAI-shaped chat-completions endpoint (`TOOL_RAG_PLANNER_URL`/`_MODEL`/`_API_KEY`, e.g. your Ollama) to turn a query + candidate tools into a validated JSON plan (`steps`/`depends_on`/`group`/`arguments_hint`); unknown `call_name`s are dropped into `missing`. Backs the `plan` meta-tool.
- `enrichment.py` — `refresh_catalog()`: the **dynamic tool catalog**. After every sync (startup before reindex, `resync_loop`, `POST /tool-rag/catalog/refresh`) it compares a catalog fingerprint (all `(tool_id, ToolRecord.content_fingerprint)` + manifest `description`/`categories`) with the stored taxonomy's; unchanged → no-op, no LLM. Changed → planner LLM (`derive_taxonomy`, 1 call) re-derives the category taxonomy (previous names fed back; a category still carried by an unchanged tool is never dropped; manifest categories always present), then `assign_tags` (1 call/server, concurrency 3) re-tags only tools whose content changed — all tools only when a *new* category appears — and writes server descriptions (manifest > LLM > upstream `initialize` instructions > "N tools: …"). Computes first, writes at the end (`_apply`); an LLM failure applies a partial result stored with an empty fingerprint so the next refresh retries (app also runs `catalog_retry_loop` 1/2/4 min). Tags go to `tool_tags` (cache) and onto `tools.tags` (embedding text); `SyncAdapter.full_sync` re-applies cached tags so syncs don't wipe them. Upstream `serverInfo`/`instructions` are captured at sync via `open_upstream_session(on_init=...)`. Tables: `server_profiles`, `tool_tags`, `catalog_taxonomy` (in `tool_db.py`).
- `catalog.py` — `ToolCatalog`: policy-scoped views over the DB for `browse_tools` / `GET /tool-rag/catalog` — `overview` (domains = servers with description + categories, categories with counts), `category` (one category or domain; tool list only for admin or `TOOL_RAG_CATALOG_LIST_TOOLS=1`), `coverage` (planner-LLM `judge_coverage` verdict strong/weak/none over the catalog + top matches with `suggested_query`; score-threshold fallback; retrieval uses `wait_for_rerank=True`), `summary_text` (~150-token per-key overview injected into the `browse_tools` description; domain names into `find_tools`'s). Counts only tools the key can see (servers, `tool_prefixes`, active, up).
- `agent.py` — `run_agent()`: the `delegate` sub-agent. Tool-calling loop on the planner model (`LlmPlanner.chat_tools`, OpenAI `tools` format) with injected `AgentTool`s (`find_tools`/`describe_tool`/`run_tool`/`get_skill`, built in `server.py` as closures over the meta-tool cores, so they run in the caller's request and policy); system prompt + skill body; bounded by `max_steps` (cap 30), `TOOL_RAG_AGENT_TIMEOUT`, 9k chars per tool result; parallel tool calls per turn; final no-tools summary turn when out of budget; MCP progress notifications if a `progressToken` was sent.
- `reranker.py` — optional `create_reranker()` factory (`TOOL_RAG_RERANKER=off|local`, default off): `LocalReranker` wraps a sentence-transformers `CrossEncoder` (default `cross-encoder/mmarco-mMiniLMv2-L12-H384-v1`, small + multilingual). When present, the retriever widens FAISS recall, then scores each `(query, tool_name+description)` pair, sigmoid-squashes to [0,1], and feeds that as the `semantic_score` — bounded to `MAX_RERANK_CANDIDATES=50` pairs/query. `local` actually runs it via `WorkerReranker`: a `python -m tool_rag.rerank_worker` subprocess (JSON lines over stdin/stdout, lock-serialized) so torch never loads in the gateway process (~100MB idle vs ~1GB). Started on demand, stopped after `TOOL_RAG_RERANKER_IDLE_SECS` (default 300, 0 = never); `TOOL_RAG_RERANKER_COLD_START=skip` (default) returns `None` while it warms → the retriever keeps embedder scores (cold vs warm queries can rank differently; `wait` blocks instead). Any worker failure → `None` + restart on next use (60s back-off after a failed start). The interface is async (`ascore`), so reranking never blocks the event loop.
- `indexer.py` — FAISS `IndexIDMap(IndexFlatIP)` over one composite text per tool (name + description + type + server + input-schema property names + tags; no document chunking). Each tool has a stable int64 id, so `remove_tool`/re-index actually drop the old vector (plain `IndexFlatIP` can't remove — that previously leaked one orphaned vector per tool per reindex). Persisted to `tool_rag.index` / `tool_rag.meta` (meta carries a `version`; a stale/old-format meta forces a clean rebuild). Supports full and incremental reindex (incremental = tools where `last_indexed_at < last_seen_at`).
- `retriever.py` — pipeline: embed query → FAISS top-K×2 (widened to ≥50 when a reranker is configured) → metadata filters (allowed_servers / permission_scope / tool_type / status=active / **server liveness**) → optional cross-encoder rerank → rank → top-K. Falls back to keyword-only DB scan if the index is empty (`fallback_used: true`); the liveness filter applies on both paths.
- `ranker.py` — final score = 1.0×semantic + 0.25×keyword + 0.15×metadata + policy penalty; deterministic tie-break on `tool_id`.
- `router.py` — Starlette handlers for `/tool-rag/retrieve|reindex|health|metrics`.

Key flow on startup: registry load → `full_sync()` (for each upstream `list_tools()` → SQLite ToolDb, + reconcile removed servers) → `refresh_catalog()` (no-op unless the tool set changed) → reindex per `TOOL_RAG_STARTUP_REINDEX` (default `full` = clean rebuild; `incremental`; `off`) → initial liveness probe + optional background loops. Reindex on demand via `POST /tool-rag/reindex {"mode": "full"|"incremental"}` — but this rebuilds **from the DB only**, it does not re-query upstreams. To pick up tool changes on a *running* upstream without a restart, set `TOOL_RAG_RESYNC_INTERVAL > 0` (background re-pull); otherwise restart.

## Conventions and constraints

- `server_id` must match `^[A-Za-z0-9._-]+$` and must not contain `__` (it's the namespace separator).
- Design rules from the spec (`content.md`): the registry/ToolDb is the source of truth; the public API must never expose the full tool list to non-admin keys; retrieval must be deterministic for identical input + index; prefer adding adapters over rewriting existing gateway code.
- The catalog never lists all tools to non-admin keys: `browse_tools`/`/tool-rag/catalog` return summaries (domains, categories, counts, ≤3 coverage matches); per-category tool lists are admin-only unless `TOOL_RAG_CATALOG_LIST_TOOLS=1`.
- Auth applies to everything except `/health` (and `/tool-rag/*` only when `TOOL_RAG_WITHOUT_AUTH=1`).
- Per-request upstream sessions mean no shared state with upstream servers (except `stateful` servers via the sticky pool) — keep handlers stateless and policy checks inside each handler.
